# 阶段四 C3b1：钉钉机器人有界重试与调用证据

## 1. 状态与边界

04C3b1 完成 Custom Webhook 机器人对供应商明确限流和服务端错误的有界重试，状态为 `implemented`。本增量没有真实发送企业群消息；机器人通知类型、静默窗口合并、提醒调度、休眠补偿和复制/导出降级继续由 04C3b2/C3b3 完成。

## 2. 重试矩阵

| 结果                         | 是否自动重试 | 最多供应商调用 | 最终事实                                                      |
| ---------------------------- | ------------ | -------------- | ------------------------------------------------------------- |
| HTTP 429                     | 是           | 3              | 耗尽后 `failed/DINGTALK_ROBOT_RATE_LIMITED`                   |
| HTTP 5xx                     | 是           | 3              | 耗尽后 `failed/DINGTALK_ROBOT_RESPONSE_ERROR`                 |
| 钉钉限流码 130101/130102     | 是           | 3              | 耗尽后 `failed/DINGTALK_ROBOT_RATE_LIMITED`                   |
| HTTP 401/403                 | 否           | 1              | 明确权限失败                                                  |
| 签名、关键词或其他业务错误码 | 否           | 1              | 明确业务失败                                                  |
| 连接失败或超时               | 否           | 1              | `unknown`，因为无法证明钉钉是否已经接收，仍禁止自动重放外部写 |

重试只发生在一次用户已创建的 delivery attempt 内，不会创建新的交付意图或绕过三次显式 attempt 上限。供应商已经明确返回 429/5xx 时按设计允许重试；没有收到响应的网络失败继续保守进入 `unknown`。

## 3. Retry-After、退避和签名

- 优先解析 `Retry-After` 秒数或 HTTP 日期，等待值限制在 250 毫秒到 30 秒。
- 没有 `Retry-After` 时使用 500 毫秒起步的指数退避，并增加最多 20% 抖动，避免多个通知同刻再次冲击限流窗口。
- 每次真实调用重新计算 timestamp 和 HMAC-SHA256 签名；固定 timestamp 只用于协议契约测试。
- 总供应商调用次数固定为 3，Job Runner 仍不会在外层盲目重放机器人写作业。

## 4. 可审计事实与隐私

机器人客户端返回 `providerCallCount` 和每次 `retryDelaysMs`。交付 handler 把这两个非敏感事实写入 `delivery_attempt.response_summary_json`，成功和失败都可复核；摘要不包含消息正文、Webhook、access token 或 Secret。

HTTP 5xx 在三次明确响应后记为 `failed`，允许用户修正后走既有“受控重试”创建新 attempt；网络超时和连接中断仍是 `unknown`，不会因 `retryable=true` 被误当作明确失败。

## 5. 自动化证据

- HMAC-SHA256、timestamp、固定请求结构和正文大小上限继续通过。
- 429 后 5xx 再成功：严格三次调用，两个 `Retry-After` 等待均被记录。
- 钉钉 130101 限流码重试后成功；HTTP 403 只调用一次。
- 三次 5xx 耗尽后保留正式日志成功事实，机器人形成部分交付失败，调用次数和等待序列写入 attempt 摘要。
- 定向 API 类型检查以及机器人协议/双通道交付 18 个用例通过。
