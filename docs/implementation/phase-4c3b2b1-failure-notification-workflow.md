# 阶段四 C3b2b1：交付失败提醒、独立通知作业与页面账本

## 1. 状态与边界

04C3b2b1 完成“正式日志明确失败 → 用户选择健康机器人 → 安全短提醒 → 通知账本可见”的闭环，状态为 `implemented`。严重风险规则配置与风险通知触发继续由 04C3b2b2 完成；本增量不会把尚未实现的风险策略描述成完成。

## 2. 冻结消息事实

通知账本新增 `message_facts_json`、供应商调用次数和等待序列。后台作业只冻结构造安全短消息所需的周期、失败阶段和脱敏错误等最小事实，不在执行时重新读取可能变化的页面状态，也不保存六字段、附件、Webhook、Token 或 Secret。

`message_facts_json` 创建后由 SQLite trigger 禁止修改；发送前使用严格 discriminated union 重新校验四类事实，并重新构造正文、核对正文哈希。事实缺失、类型漂移或哈希不一致都会在外部调用前失败。

## 3. 失败提醒门禁

- 只接受属于当前用户周报、通道为 `dingtalk_log` 且状态为 `failed` 的交付意图。
- `unknown/needs_review` 明确拒绝，因为可能已创建正式日志，不能向群里误报失败。
- 请求必须携带当前周报乐观锁版本和明确选择的健康机器人；不会静默挑选任意群。
- 错误摘要移除 Authorization、Token、Secret、Webhook 等键值，清理控制字符并限制 240 字。
- 账本按失败 intent + `submission_failure` + intent 状态版本去重；内容相同且在静默窗口内时继续使用既有合并机制。

## 4. 独立通知作业

新增 `weekly-report.notification` handler，和正式日志/群摘要交付 handler 分离：

- 入队事务同时创建通知账本、单次 job、幂等响应和审计事件。
- 执行前重新检查机器人仍启用、健康且当前凭证可读。
- 使用 C3b1 的 429/5xx 有界重试；成功/失败/unknown、请求 ID、供应商调用次数和等待序列写回账本。
- 网络超时或连接中断进入 `unknown` 并抛给 Job Runner，重复执行会在外部调用前被状态门禁拒绝。
- 明确失败可由新的状态版本重新触发；结果未知不允许自动重放。

## 5. 租约恢复

通用 Job Runner 的人工复核恢复已覆盖三个业务对象：Git 批次、周报钉钉交付和机器人通知。进程重启发现租约过期，或 handler 异常退出时：

- `weekly-report.notification` 的 sending 账本转为 unknown；
- `weekly-report.delivery` 的 running intent、周报通道状态以及关联机器人账本一起转为 unknown；
- 均写入 `RESULT_REQUIRES_REVIEW`，不只修改 job 而留下业务页面假状态。

## 6. API 与页面

- `GET /weekly-reports/:id/notifications` 返回通知类型、状态版本、合并次数、计划/发送/跳过时间、调用次数、等待序列和非敏感错误。
- `POST /weekly-reports/:id/notifications/failure` 使用幂等键创建或返回失败提醒事实。
- 周报页面仅在正式日志明确失败且已选择健康机器人时开放“发送失败提醒”。二次确认明确消息边界，unknown 时按钮保持禁用。
- 页面新增机器人通知账本表，展示类型、状态、状态版本、静默合并数、供应商调用证据、错误/跳过原因和更新时间。

## 7. 自动化证据

- 明确失败生成安全短摘要，敏感错误被 `[REDACTED]`，完整周报正文未进入机器人调用。
- 同状态版本重复请求返回原 job，不产生第二次外部调用。
- 正式日志 unknown 请求失败提醒被拒绝。
- 失败提醒网络超时进入 unknown，再次执行不调用机器人。
- 租约过期通知和交付业务事实随 job 一并进入 unknown。
- 定向 API 3 个文件 16 个用例、Web 6 个文件 15 个用例通过。

## 8. 后续增量

04C3b2b2 将增加机器人严重风险代码配置、只对当前版本中已配置严重规则生成风险通知，以及对应页面选择/账本证据。随后 04C3b3 实现 Asia/Shanghai 提醒调度、休眠宽限补发/超时 skipped 和复制导出降级。
