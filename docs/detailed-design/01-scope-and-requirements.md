# 01 范围与需求追踪

## 1. 目的与范围

系统面向单个 Windows 用户，把 14 个本地 Git 仓库、公司 GitLab、个人 Jira 任务、现有 Excel 任务表、钉钉六字段周报和季度绩效材料串联成一个本机控制台。系统是个人研发工作台，不是团队 Jira/GitLab 的替代品，也不是无人值守的自动执行代理。

### 1.1 范围内

- 发现、登记、刷新和管理 `D:\company` 一级目录下的 Git 仓库。
- 从 GitLab 读取项目、分支、Commit、MR、Pipeline、Tag、Release 和只读成员信息。
- 使用本地 `git.exe` 执行白名单内、受约束且经过确认的 Git 操作。
- 从 Jira `/rest/api/2/*` 同步当前用户任务、字段、状态和工时。
- 对三类现有 Excel 工作表进行预检、映射、纠错提示和提交导入。
- 建立任务与分支、Commit、MR、Pipeline 的证据关系。
- 汇总六字段周报，保留生成及人工修改版本，经确认后提交钉钉正式日志。
- 使用加签 Custom Webhook 机器人发送摘要和提醒。
- 使用外部 AI 模型做聚合、去重、分类和文字建议，默认仅发送元数据。
- 汇总季度成果、映射指标、生成自评和评分建议，人工调整后导出 Excel/Word。
- 本地调度、审计、备份、失败重试和操作恢复。

### 1.2 范围外

- AI 读取源代码、完整 diff、附件内容或客户数据。
- AI 或后台任务自动 Commit、Push、修改 Jira、提交周报或确定绩效分数。
- 强制推送、硬重置、自动解冲突、批量 Merge/Rebase、自动删未合并分支、任意 Shell。
- 替代 GitLab/Jira 的权限、评审、CI/CD 或任务工作流。
- 依赖“AI小钉”调用公司外部系统。
- 首版默认启用 GitLab/Jira 群机器人。
- 向公司自动提交最终绩效材料。
- 多用户、局域网共享、互联网公开访问、集中式服务端部署。

## 2. 参与者与职责

| 参与者 | 职责 | 不允许 |
|---|---|---|
| 当前 Windows 用户 | 配置凭证、确认身份、选择仓库、批准写操作、编辑周报、决定绩效 | 绕过预检执行被禁止命令 |
| 本机 Web 控制服务 | 页面、API、事务、持久化、编排、审计 | 直接持有明文密钥、越过 Git Worker 执行任意命令 |
| Git Worker | 采集仓库状态，执行经过批准的结构化 Git 动作 | 访问白名单外路径、接受自由文本 Shell |
| 后台调度器 | 增量同步、元数据刷新、提醒、备份、重试 | 执行需人工确认的业务写操作 |
| GitLab | 代码托管和只读研发元数据来源 | 被系统当作本地工作区状态来源 |
| Jira | 任务事实主来源 | 被 AI 或本系统自动改变状态 |
| Excel | Jira 不可用时的兜底及排期/工时补充 | 覆盖已有 Jira 主数据、回写原文件 |
| 钉钉日志 | 正式周报主通道 | 被 Webhook 摘要替代 |
| Custom Webhook | 提醒和简短摘要 | 接收完整周报或敏感凭证 |
| 外部 AI | 生成建议、聚合和表述 | 执行工具、作最终业务决定、接收禁止数据 |

## 3. 核心业务规则

### 3.1 通用规则

- BR-GEN-001：所有时间入库为 UTC 时间戳，业务日期按 `Asia/Shanghai` 解释和展示。
- BR-GEN-002：业务对象使用内部不可变 ID；外部 ID 仅作为带来源命名空间的唯一键。
- BR-GEN-003：任何外部写请求必须携带幂等键；同一业务动作重放不得生成重复正式结果。
- BR-GEN-004：删除优先采用禁用/归档；证据、审计、已提交报告和已导出快照不得物理级联删除。
- BR-GEN-005：页面显示“上次成功同步时间”和“数据可能过期”状态，不能把缓存当成实时事实。

### 3.2 Git 规则

- BR-GIT-001：仓库白名单以规范化真实路径保存；只允许位于 `D:\company` 下且经用户确认的仓库。
- BR-GIT-002：预检保存仓库 ID、操作、参数、HEAD、当前分支、工作区摘要和远端跟踪状态。
- BR-GIT-003：批准后执行前，HEAD、分支、工作区关键条件与预检不一致则该仓库拒绝执行并要求重新预检。
- BR-GIT-004：批量操作逐仓库执行，单仓库失败不回滚已经成功的其他仓库；结果必须逐项展示。
- BR-GIT-005：`pull` 只允许 `--ff-only`；Push 不允许 force 变体；创建分支必须基于已解析且存在的基线引用。
- BR-GIT-006：Stage 只接受预检中明确列出的路径集合，Commit message 不能为空，且提交和推送是两个独立批准动作。

### 3.3 任务和导入规则

- BR-TSK-001：Jira 是相同 issue key 的主记录；Excel 只能补充缺失的计划日期、到期日和工时。
- BR-TSK-002：增量同步采用 `(updated, issueKey)` 复合水位，时间窗口重叠回读以避免同秒更新遗漏。
- BR-TSK-003：来源中消失的任务不直接删除，标为“本次查询不可见/超出范围”，只有全量核对后才更新可见性。
- BR-XLS-001：父任务 ID/名称同时为空时从同一工作表的最近上一条有效父任务继承；跨工作表不继承。
- BR-XLS-002：父任务容器行没有子任务和经办人时不生成个人工作项，但可更新父任务维度。
- BR-XLS-003：Excel 日期可能是日期类型、序列值或公式结果；统一转换为业务日期，并记录原始单元格值。
- BR-XLS-004：人日以原始 G 列工时为判断基础；G 为空时 H 的公式结果 0 不代表工时为 0，仍应导入为 `null`。
- BR-XLS-005：导入先预检、再确认提交；原始文件不回写。

### 3.4 周报与绩效规则

- BR-WR-001：周报覆盖周期与填写日期分开保存；默认周期为本周，填写日期为本周最后一个工作日。
- BR-WR-002：周报必须包含六个正式字段；问题字段无内容时显式为“暂无”。
- BR-WR-003：生成内容必须保存来源快照；后续源数据变化不应悄悄改写已生成版本。
- BR-WR-004：确认锁定一个明确版本；已确认版本再编辑时生成新草稿并使旧确认失效，必须重新确认。
- BR-WR-005：正式日志提交成功和机器人通知成功是两个独立结果；日志成功、机器人失败属于部分交付，不能重提日志来补通知。
- BR-PERF-001：成果按业务结果聚合，不按 Commit 数量或代码行数计分/估工时。
- BR-PERF-002：AI 分数是带理由的建议；最终分项分数由用户确认，总分只由选定的版本化公式计算。
- BR-PERF-003：导出是冻结快照；源数据变化不修改历史导出。

## 6. 冲突、歧义与设计裁决

| 编号 | 原始歧义/冲突 | 详细设计裁决 |
|---|---|---|
| D-001 | “所有写操作均需确认”可能包含本地缓存/审计写入 | 仅业务副作用写操作需确认；缓存、同步游标、审计、草稿自动保存不逐次确认，但必须可见和可追踪 |
| D-002 | 周报字段模型含日期外五段正文，但称“六字段” | 六字段固定解释为填写日期、近期目标、本周内容、下周计划、协助问题、其他补充；附件和接收范围是提交元数据 |
| D-003 | 钉钉日志 OpenAPI 的具体权限/版本未证实 | 设计为 `DingTalkLogPort`，上线前必须在公司组织能力探测；失败时只允许导出/复制，不允许机器人替代正式日志 |
| D-004 | 自建 GitLab/Jira 版本未知 | 禁止依赖仅新版本字段；连接测试保存能力矩阵，分页和字段解析采取兼容策略 |
| D-005 | `updated` 单游标可能漏同一时间更新 | 使用 `(updated, issueKey)`、重叠窗口和 upsert 去重，不使用单时间戳硬切分 |
| D-006 | Excel H 列公式在 G 为空时可能得到 0 | 以 G 原始值是否为空决定工时/人日为空语义，H 仅作校验或显示 |
| D-007 | “预检后确认”是否可一次批准多仓库 | 可以一次批准一个批次，但每个仓库保存独立快照、独立结果；批次批准不允许中途新增仓库或参数 |
| D-008 | “所有 AI 版本”范围不明确 | 每次模型请求的净化输入摘要、模型配置版本、原始输出、解析结果和后续人工派生版本均保留 |
| D-009 | 绩效公式来源未给出 | 系统支持版本化公式配置；没有经用户确认的指标、权重、上限和取整规则时禁止生成最终总分 |

## 7. 必须由企业环境确认的配置

这些事项不阻止详细设计，但构成对应功能进入开发完成/生产可用的验证门：

1. 公司 GitLab 版本、PAT 权限范围、API 分页行为、项目路径大小写规则。
2. Jira 版本、PAT 或 OAuth 策略、可用字段 ID、状态集合、Sprint/父子/工时字段。
3. 钉钉应用类型、企业内部应用权限、日志模板读取/写入能力、接收人/群字段和附件限制。
4. `uTwin产研创新部周报` 的准确六字段名称、顺序、必填性、字符上限。
5. Custom Webhook 可用消息类型、频控、加签算法和群标识获取方式。
6. 法定节假日/调休日历来源；默认“工作日”不能只按周一至周五长期硬编码。
7. 季度绩效模板、指标、权重、分数范围、取整规则和 Excel/Word 格式样例。
8. 数据留存期限、备份保存位置及企业对外部 AI 供应商的白名单/数据政策。

## 8. 需求追踪方法

- 每个 API、数据表、页面和测试用例必须引用至少一个需求 ID。
- 每个需求至少有一个正向验收和一个关键异常/安全测试。
- 需求状态采用 `proposed / designed / implemented / verified / accepted`；本阶段所有表内需求最高只能标为 `designed`。
- 后续不得用“页面存在”代替功能验收；验收必须验证业务结果、证据、审计、幂等和恢复行为。
