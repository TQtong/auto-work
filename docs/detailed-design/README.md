## 1. 文档目标

本套文档把 `design.md` 中的方案级描述展开为可实施、可测试、可验收的详细设计。它不包含业务代码，也不把功能压缩为最小版本。后续开发应以本目录的边界、数据语义、状态机、接口契约、安全约束和验收标准为准；发现实现条件与文档不符时，应先更新决策记录和需求追踪矩阵，再改实现。

## 3. 设计阅读顺序

1. 先阅读 01，明确完整范围、需求 ID 和尚未确认的企业配置。
2. 阅读 02、03，理解运行边界、领域关系和持久化语义。

4. 前后端以 08、09 进行联调；安全和后台任务同时遵循 10。
5. 以 11 建立测试资产，以 12 安排阶段和发布门禁。

## 4. 全局设计原则

- **本机优先**：只绑定 `127.0.0.1:3760`，只访问明确加入白名单的本地仓库。
- **读写分离**：外部数据读取可自动调度；Git 写、周报正式提交、绩效最终确认等业务写操作必须由用户明确确认。
- **预检与执行隔离**：所有危险写操作先生成不可变预检快照，再批准；执行前重新验证关键前置条件。
- **事实与生成内容分离**：Jira、Git、GitLab、周报和手工输入是事实/证据；AI 输出是可追踪、可编辑、不可自动执行的建议。
- **来源可追溯**：周报段落、季度成果和评分说明都能回溯到证据或人工输入。
- **凭证不落明文**：数据库只存凭证引用和掩码元数据；Windows 使用当前用户 DPAPI，Docker 使用持久主密钥和 AES-256-GCM 认证密文。
- **失败可恢复**：跨系统操作不假装原子事务，通过状态机、幂等键、重试记录和人工恢复实现最终一致。
- **版本化**：字段映射、生成快照、AI 输入输出、人工编辑、导出模板和评分公式全部有版本。
- **保守降级**：外部服务不可用时保留本地功能；不能自动完成时提供明确的人工复制/导出方案，不静默丢失。

## 5. 权威性与变更控制

- 业务目标和已确认企业环境以 `design.md` 为来源基线。
- 本目录给出更细的实现语义；若与 `design.md` 文字冲突，以“更安全、需要人工确认、可追溯、不丢数据”的解释为默认，并在 12 中登记决策。
- 外部平台能力必须在目标公司实例上通过“连接测试/能力探测”确认。公开官方文档只证明平台一般能力，不证明公司实例版本、权限或套餐已开放。
- 任何需求变更至少更新：需求条目、相关专题设计、API/数据模型、测试用例和追踪矩阵。

## 6. 本阶段明确不做的事

- 不编写前端、后端、数据库迁移、脚本或部署代码。
- 不连接或修改公司 GitLab、Jira、钉钉数据。
- 不向外部模型发送任何企业数据。
- 不提交周报、不推送 Git、不创建或修改 Jira 任务。
- 不自动决定绩效得分，不自动向公司提交绩效材料。
